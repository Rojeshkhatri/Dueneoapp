# 1. Executive Summary

Dueneo is a focused browser-first platform for practical tools and lightweight classic games. The product is built around three promises:

1. **Useful:** Each page solves a real user problem immediately.
2. **Private:** Tool processing happens locally in the user's browser wherever technically possible.
3. **Fast:** Pages are static, lightweight, mobile-first, and built for search engines and users.

Dueneo is not a heavy SaaS. It is not a login-based application. It is not a graphics-heavy gaming portal. It is a clean, durable, SEO-first utility platform containing 100 high-value tools and 15 classic games that can run from a static site.

The whole system is designed so humans and AI coding agents can work safely from the same document. Codex can implement tools and tests. Hermes or OpenClaw can research SEO improvements and generate pull requests. GitHub Actions validates every change. Cloudflare Pages deploys production.

# 2. Non-Negotiable Product Principles

## 2.1 Browser-first

Every tool must run in the browser unless this Bible explicitly approves another architecture. The default answer to new feature ideas is:

> Can this run locally in the browser with no backend and no upload?

If the answer is no, the feature is excluded from the current Dueneo scope.

## 2.2 Privacy-first

For tools that handle files, passwords, invoices, text, JSON, images, or PDFs:

- Do not upload the user's input.
- Do not log tool input to analytics.
- Do not store personal data unless the user chooses local save.
- Do not send generated passwords, invoices, JSON, text, or files to any third party.
- Show a short privacy note near the tool area.

Standard privacy note:

> Your file/data is processed locally in your browser. It is not uploaded to Dueneo.

For pages that include ads or analytics, the privacy policy must disclose ad/analytics scripts separately. The local-processing promise applies to the tool's input and output.

## 2.3 One design system

All pages must look and feel like Dueneo:

- Same header.
- Same footer.
- Same search.
- Same spacing.
- Same card style.
- Same ad locations.
- Same FAQ style.
- Same related-tool style.

Only the inner tool/game logic changes.

## 2.4 Production quality from the first public release

Every published page must have:

- Working tool/game.
- Useful surrounding content.
- Unique metadata.
- Canonical URL.
- Structured data where appropriate.
- Related links.
- Mobile layout.
- Accessibility basics.
- Error states.
- Performance budget.
- No broken internal links.

## 2.5 SEO is product work

SEO is not a separate trick. SEO means improving the website itself:

- Better titles.
- Better descriptions.
- Better page content.
- Better internal links.
- Better structured data.
- Better speed.
- Better UX.
- Better crawlability.

AI agents may help with SEO, but they must change the source code through pull requests, not through invisible off-site edits.

# 4. Domain and URL Strategy

Use the root domain for the tools brand:

```text
dueneo.com/
dueneo.com/image-compressor/
dueneo.com/pdf-merge/
dueneo.com/json-formatter/
dueneo.com/invoice-generator/
dueneo.com/games/sudoku/
```

Do not hide primary tools under deep paths such as `/tools/image/image-compressor/`. Short root-level URLs are easier to remember, easier to share, and cleaner in search results.

## 4.1 URL rules

Good:

```text
/image-compressor/
/pdf-merge/
/json-formatter/
/games/sudoku/
```

Bad:

```text
/tool?id=123
/tools/all/imagecompressor
/image_compressor
/app/tools/free-online-image-compressor-tool
```

## 4.2 Trailing slash

Use one canonical style everywhere. Recommended:

```text
/image-compressor/
```

Redirect non-trailing slash to trailing slash or configure the framework to output one consistent canonical URL.

## 9.1 Recommended stack

```text
Astro          Static pages and SEO shell
React          Interactive tools/games
TypeScript     Type safety
Tailwind CSS   Utility styling and design tokens
Vite           Build system through Astro
```

## 9.2 Why Astro + React

Astro is used for static HTML, SEO pages, metadata, and page structure. React is used only where interactivity is required. This prevents every page from shipping a large JavaScript bundle.

Rule:

```text
Content shell = Astro
Interactive tool = React island
Heavy processing = Web Worker
```

# 10. Browser-Only Engineering Standards

## 10.1 Data handling

Tool input must remain in memory, localStorage, IndexedDB, or downloaded output unless the user explicitly exports it.

Sensitive tools must avoid localStorage by default:

- Password Generator.
- Password Strength Checker.
- JWT Decoder.
- Hash tools.
- Invoice Generator unless user enables local save.

## 10.2 Web Workers

Use Web Workers for:

- Image compression.
- Large image conversion.
- PDF merging/splitting.
- PDF rendering.
- Large text diff.
- Large CSV/Excel conversion.

## 10.3 Lazy loading

Heavy libraries load only after user intent:

```text
User opens page: no heavy PDF/image library yet.
User selects file: load tool library.
```

## 10.4 Memory safety

File tools must:

- Show file size before processing.
- Reject unreasonable file sizes with friendly message.
- Allow cancellation where feasible.
- Release object URLs after use.
- Avoid keeping multiple large copies of files in memory.

## 10.5 Browser compatibility

Support latest stable versions of:

- Chrome.
- Edge.
- Firefox.
- Safari.
- Mobile Safari.
- Chrome Android.

For unsupported browser APIs, show fallback guidance.

# 11. SEO Strategy

## 11.1 SEO goal

Each tool and game page should target one clear search intent. Dueneo should not rely on one homepage ranking. Every tool page is a search landing page.

## 11.2 Google SEO principles

Google SEO starts with making pages useful, crawlable, understandable, and technically sound. Dueneo follows these rules:

- Clear descriptive page titles.
- Unique meta descriptions.
- Helpful content around the tool.
- Static HTML for crawlers.
- Valid canonical URLs.
- Structured data where appropriate.
- Useful internal links.
- Fast loading.
- Mobile-friendly layouts.
- No thin pages.

## 11.3 Bing SEO principles

Bing optimization is not separate from good SEO, but Dueneo should explicitly support Bing:

- Submit sitemap to Bing Webmaster Tools.
- Use IndexNow for changed URLs.
- Maintain clean XML sitemaps.
- Use structured data.
- Use descriptive titles and content.
- Avoid spammy generated pages.

## 11.4 IndexNow

Dueneo uses IndexNow only for URLs that are added, updated, or deleted. The script should read changed pages from the build or Git diff and submit those URLs.

Example request shape:

```json
{
  "host": "dueneo.com",
  "key": "INDEXNOW_KEY",
  "keyLocation": "https://dueneo.com/INDEXNOW_KEY.txt",
  "urlList": [
    "https://dueneo.com/image-compressor/",
    "https://dueneo.com/pdf-merge/"
  ]
}
```

IndexNow submission is a discovery signal, not a guarantee of indexing.

## 11.5 Metadata rules

# 12. Monetization Strategy

## 12.1 Ad philosophy

Dueneo uses simple, non-obstructive ads. The page must remain useful even if ads fail to load.

Maximum default:

```text
Ad Slot 1: after tool/game
Ad Slot 2: after FAQ/content
```

## 12.2 AdSense

AdSense is the primary starting ad network.

Rules:

- Do not place ads near copy/download/play buttons.
- Do not label ads misleadingly.
- Use `Advertisement` or `Sponsored` only if a label is needed.
- Do not use popups or forced interstitials.
- Reserve ad slot space to reduce layout shift.
- Exclude sensitive pages if needed.

## 12.3 Media.net

Media.net is included as a controlled monetization network, not hardcoded into every page.

Testing plan:

```text
Image tools: compare AdSense vs Media.net on second slot.
PDF tools: compare AdSense vs Media.net on second slot.
Business/finance tools: compare both networks carefully.
Games: test only after UX is stable.
```

Do not place both networks so densely that ads overwhelm content.

## 12.4 Ad rules by page type

```text
Tool pages: up to 2 ads.
Game pages: up to 2 ads, never inside game board.
Legal pages: no ads.
Contact page: no ads.
Privacy page: no ads.
Homepage: 0-1 ad only after content, optional.
Category pages: 0-1 ad, optional.
```

## 12.5 Revenue Agent responsibilities

The Revenue Agent tracks:

- RPM by category.
- Viewability.
- Ad load impact.
- User engagement.
- Bounce rate.
- Core Web Vitals impact.

The Revenue Agent may propose:

- Network swaps.
- Slot removal.
- Slot repositioning.
- Category-specific settings.

It must never propose deceptive placements.

# 19. Security and Privacy

## 19.1 Content Security Policy

Recommended starting CSP:

```text
default-src 'self';
script-src 'self' https://pagead2.googlesyndication.com https://www.googletagservices.com https://*.media.net;
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob: https:;
font-src 'self' data:;
connect-src 'self' https://*.google.com https://*.googlesyndication.com https://*.media.net https://api.indexnow.org;
worker-src 'self' blob:;
object-src 'none';
base-uri 'self';
frame-ancestors 'self';
```

CSP must be tested with actual ad and analytics providers before enforcing.

## 19.2 Secrets

Never expose:

- API keys.
- Cloudflare tokens.
- GitHub tokens.
- Ad network account secrets.
- IndexNow private control beyond public key file requirements.

## 19.3 Sensitive tools

Sensitive pages must avoid unnecessary scripts when possible:

- Password Generator.
- Password Strength Checker.
- JWT Decoder.
- Hash tools.

For these pages, consider reduced analytics and reduced ads if privacy/trust is more important than revenue.

# 25. Coding Standards

## 25.1 TypeScript

- Strict mode enabled.
- No `any` unless justified.
- Tool input/output types defined.
- Shared utilities tested.

## 25.2 React

- Tool components should be isolated.
- Avoid global state unless needed.
- Use controlled inputs where practical.
- Use reducers for complex tools.
- Avoid unnecessary re-renders for large text/files.

## 25.3 Astro

- Pages should be statically generated.
- Metadata generated from registry.
- Tool component hydrated only when required.

## 25.4 CSS/Tailwind

- Use design tokens.
- Avoid random one-off colors.
- Keep consistent spacing.
- Use responsive classes consistently.

## 25.5 Dependencies

A dependency is allowed only if:

- It solves a real problem.
- It works in the browser.
- It does not require a backend.
- It is reasonably maintained.
- It does not bloat unrelated pages.
- It has acceptable license terms.

# 31. Final Operating Rule

Dueneo succeeds by being consistently useful, fast, private, and trustworthy. The goal is not to publish the most pages. The goal is to make each of the 100 tools and 15 games good enough that users would return, share them, and trust the brand.

Every decision should be tested against this question:

> Does this make Dueneo more useful, faster, more trustworthy, or easier to discover?

If not, do not ship it.
